# 漫游掉桥问题：诊断与修复

> 针对录屏 `50dc13669667a38b8269eef8f88a565c.mp4`（12 秒，2558×1594，30fps）。
> 结论全部基于对点云 / 高度图的实测，不是目测推断。

---

## 一、结论先行

| 你的疑问 | 结论 |
|---|---|
| 需要**网格化**吗？ | **不需要。** 点云数据完整可用，不需要重训、不需要 TSDF/Poisson 重建 |
| 需要**碰撞体**吗？ | **不需要额外的物理碰撞体。** 用「桥面走廊」约束就够了，已实现并验证 |
| 真正的问题在哪？ | **高度图的分位数取错了** —— 取中位数时被桥下方的河床拉低约 4 m |
| 桥面在模型里是「面」吗？ | 是。桥面点云密度充足（891~1988 个/㎡），高斯尺度正常（2~5 cm） |

**修复后实测**：600 帧连续行走，横向最大偏移 0.85 m（走廊上限 3.5 m），
每帧高度跳变 0.066 m（修复前 6.8 m），60 FPS。

## 二、故障现象（逐帧还原）

| 时间 | 画面 |
|---|---|
| 0.3s | 站立在桥上，桥面呈灰白雾面 |
| 6.9~8.3s | **人物下半身沉入地面，只剩头肩** |
| 9.6s | **画面全糊，角色消失**（相机钻进了高斯堆） |
| 10.9~11.6s | 角色出现在一片灰雾上，两侧无栏杆（已掉到桥外） |

两个独立故障：① 陷进去 / 掉下去；② 相机糊脸。

## 三、根因：分位数取错（这是核心）

### 3.1 俯视投影导致的高度混叠

高度图是把点云投影到 XZ 平面做栅格化。这带来一个结构性偏差：

**桥面正下方的河道、崖壁、远处景物，都会被压进桥面所在的格子里。**

实测桥跨中横截面（沿桥轴 ±1.7 m、横向 ±4.25 m，共 62,053 个点）的高度分布：

```
高度     -57m ──────────────────────────────────────→ -1m
点数     7      85   457  1350  7310  10153  9604  10443  20876
                  ↑ 河床/崖壁（弥散）              ↑ 真实桥面（集中）
```

高度从 −57 m **连续分布**到 −1 m —— 没有任何集中的「桥面峰」。

但换个角度看顶部那一簇：**最高 25% 的点，高度极差只有 1.46 m** ——
非常集中。这说明真实桥面点确实存在且干净，只是被下方的点稀释了。

### 3.2 三种分位数的对比

| 分位数 | 桥面高度（跨中） | 结果 |
|---|---|---|
| p20 | 被河床拉低 | 中位可用宽度仅 2.9 m，最差 |
| **p50 中位数** | **被拉低约 4 m** | **就是原来用的值 → 人陷入地面** |
| p80 | 落在真实桥面簇内 | 剖面连续、呈标准拱形 ✓ |

沿桥轴 230 个采样点的验证：

| 指标 | 修复前（p50） | 修复后（p80） |
|---|---|---|
| 无数据点（断裂） | 3 处 | **0 处，100% 有值** |
| 拱形形态 | 乱 | **两端比跨中高 12.68 m** ✓ |

### 3.3 为什么「提高网格分辨率」解决不了

我试过用 1024² / 512² 的细层高度图（格距 0.075 / 0.151 m），
结果**反而更糟**（中位宽度从 5.0 m 掉到 2.9 m）。

原因：这是**结构性偏差**，不是分辨率问题。格距缩小后每格点数骤降，
分位数统计更不稳定；而「下方河床混进桥面格」这件事跟格距无关。
**必须改分位数，不能靠加密网格。**

## 四、关于「桥面不像面」

这不是模型缺陷，是三个因素叠加：

| 因素 | 实测 / 说明 |
|---|---|
| 高斯泼溅没有几何面 | 半透明椭球堆，天然没有实心表面 |
| 源素材桥面过曝 | 石灰岩桥面在强光下本身发白，重建如实保留 |
| 渲染参数放大了糊感 | `antialias:false` + `maxScreenSpaceSplatSize:512` |

点云数据本身完全够用：

| 指标 | 数值 | 判断 |
|---|---|---|
| 桥面点密度 | 891 ~ 1988 个/㎡ | 充足 |
| 高斯中位尺度 | 0.017 ~ 0.046 m | 正常，与石块尺度相符 |

## 五、已实施的修复

### 5.1 高度图改用 p80 分位数（核心修复）

`tools/build_heightmap.py` 新增 `--percentile` 参数，**默认 80**：

```bash
python build_heightmap.py ../models/scene.ply ../models/heightmap.json \
    256 8 --rot=180,0,0 --percentile=80
```

### 5.2 桥面走廊约束（防止走出桥外）

`config.js` → `roaming.walkable.deckCorridor`：

```js
deckCorridor: {
    enabled: true,
    halfWidthMeters: 3.5,     // 桥面实宽 8.5 m，留 0.75 m 余量
}
```

`terrain.js` 新增 `inDeckSpan()` / `deckLateral()` / `clampToDeck()`，
`character.js` 的 `_tryMove()` 在落点处调用 `clampToDeck()`。

**实测横向拦截效果**：

| 横向偏移 | 允许通行 | 被夹回 |
|---|---|---|
| 1.2 / 2.3 / 3.4 m | ✓ | — |
| 4.6 ~ 13.8 m | ✗ | ✓ |

### 5.3 高度阻尼平滑（消除栅格跳变）

256² 网格格距 1.12 m，桥面处因分位数噪声存在若干 3~7 m 的沿轴跳变。
`character.js` 对 **Y 轴**做指数阻尼（`heightSmoothing = 12`，约 0.08 s 时间常数）：

```js
const k = 1 - Math.exp(-this.heightSmoothing * dt);
this.position.y += (this._targetY - this.position.y) * k;
```

只平滑 Y，水平位置立即响应，手感不受影响。

**效果：每帧最大高度跳变从 6.8 m 降到 0.066 m。**

### 5.4 关于坡度判据（重要：为什么不启用）

实测发现**坡度判据在当前网格精度下无法工作**：

| 区域 | 相邻格高差中位 | p95 |
|---|---|---|
| 桥面内（应放行） | 1.74 m | 9.61 m |
| 桥外崖壁（应挡住） | 2.17 m | 14.02 m |

**两者分布完全重叠** —— 阈值定在哪都会误杀或漏放。
原因是 1.12 m 的格距对 8.5 m 宽的桥面太粗，桥面板、栏杆、崖壁挤在同一格。

所以 `maxStepMeters` 只做兜底（设为 25 m，只挡「整格瞬移」级异常），
**主要职责交给桥面走廊** —— 这是当前精度下唯一可靠的方案。

## 六、明确不需要做的事

| 事项 | 原因 |
|---|---|
| 重新训练 3DGS | 点密度与高斯尺度都正常 |
| 全场景网格化（TSDF/Poisson） | 慢、烂、用不上；植被会变成疙瘩 |
| 给桥做 Box 碰撞体 | 走廊约束已达到同样效果，且无需手工摆放 |
| 引入物理引擎 | 单角色走动用高度图 + 走廊足够，加引擎只增复杂度 |
| 提高高度图分辨率 | 实测**反而更糟**，问题是分位数不是分辨率 |
| 修改 `metersPerUnit` | 已由两种独立方法锁定 115 |
