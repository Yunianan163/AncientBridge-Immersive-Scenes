### 踩的坑（都靠实验定位，不是猜的）

- **★ 匾额被屋檐整个盖住。** 第一版屋檐出挑 0.08、匾额缩在檐下 0.077，
  从 36° 俯角看过去只剩檐下一条黑影。判据：设匾额顶 `(z_p,y_p)`、屋檐前缘 `(z_e,y_e)`、`z_e > z_p`，
  要求 `y_p + (z_e−z_p)·tanθ ≤ y_e` —— 出挑越大越难满足，**降俯角救不回来**。
  正解：**出挑收到 0.005，匾额略微探出屋顶前缘**。同时 `SHOP.phi` 0.94 → 1.10。
- **★ `flyDist` 0.40 太近**，屋顶糊满屏幕。按屏高反算：`d ≈ 占屏比 × 2tan(fov/2) / 模型高`，

- **六角台基描边整体歪 30°**：`CylinderGeometry` 的圆用 `(sinθ, cosθ)`，我手写描边用了 `(cosθ, sinθ)`。
  统一用 `sin/cos` 即对齐。
- **四棱锥屋顶面宽方向比屋身还窄**：底面是正方形，面距只有 `r/√2`。
  `r = 面距·√2`，再 `roof.scale.set(1.24,1,1)` 拉成长方 plan。
- **台基半径 0.325 是屋身宽的 2.8 倍**，像祭坛不像铺子 → 收到 0.205。
- **无头验证时序**：`window.__scene3d` 是在 `buildMap` 之后**同步**挂的，而箭头放出与载入层退场
  排在 `setTimeout(260)` 里 —— 只等 `__scene3d` 就断言，会打在"画面上还是载入层"那一帧

## 追问：文创坊「屋顶拉伸变形」的修复（17:10 用户报障）

> ⚠️ **本节更正上面「### 四处几何问题」里的一条 —— 那条给的修法是错的，正是变形的来源。**
> 上面写「`roof.scale.set(1.24,1,1)` 拉成长方 plan」，实际这行代码本身制造了变形。

### 根因：`T·R·S` —— scale 先于 rotation 生效

`CylinderGeometry(·, r, ·, 4)` 的四个顶点落在坐标轴上，**没转之前是个菱形**。
原代码：

```js
roof.rotation.y = Math.PI / 4;
roof.scale.set(1.24, 1, 1);     // ✗
```

等价于「**先把菱形沿 x 拉长，再整体转 45°**」→ 得到的是**斜的菱形**
（长轴指向前左/后右 45°），不是长方形。四个角朝斜向戳出去。

**可算的判据**（不用肉眼）：修正前底面四角为 `(±0.1365, ∓0.1365)` 与 `(∓0.110, ∓0.110)`；
前棱从 `(−0.1365, 0.1365)` 连到 `(0.110, 0.110)`，在 x=0（匾额正中）处 **z = 0.1218**，
而匾额贴在 z = 0.114 —— 前棱比匾额还靠前 0.008，必然盖住它。
这同时解释了截图里「匾额被压」「左边灯笼不见」（对称的右角吃掉了它）。

### 修法：两步都烘进 geometry

```js
const ROOF_HX = 0.137, ROOF_HZ = 0.110, ROOF_H = 0.084;   // 举高 0.070 太扁，读成一块盖板
const g = new THREE.CylinderGeometry(Math.SQRT2 * 0.08, Math.SQRT2, ROOF_H, 4);
g.rotateY(Math.PI / 4);        // 菱形 → 轴对齐正方（半边长 = 1，r 取 √2 就免了心算）
g.scale(ROOF_HX, 1, ROOF_HZ);  // 正方 → 目标长方形
```

`r` 取 `√2` 让底面半边长 = 1，之后填什么比例就是什么。
描金 `LineLoop` 的顶点也改用 `ROOF_HX / ROOF_HZ` 生成 —— 否则会出现
「描线是长方形、屋面是斜菱形」的错位。

### 顺手修的第二个问题：灯笼是纯自发光 → 平贴色片

拉近看，灯笼是一个**零明暗过渡的粉色圆片**，且悬空无连接件。
`emissive` 在球面上是均匀的，几何上不可能有过渡。改：
- `emissive 0xd8734a → 0xb5483a`（深本色），呼吸值 `0.78±0.22 → 0.31±0.11`

## 19:0x —— 修「点箭头切场时跳一下」

用户给了一段录屏（ScreenSketch mp4），要求：切换时不要跳，**直接定格在模型那里**。

### 根因：飞行途中相机朝向被冻住，动画结束才被一把拽正

`tick()` 的飞行分支只 lerp 了 `camera.position` 与 `controls.target`
（`index.html` 第 2043-2044 行附近），**从没更新相机朝向**；
而唯一会 `lookAt(target)` 的 `controls.update()` 被放在 `else` 分支里、且要求 `controls.enabled`
（`flying` 时它被设成 false）。所以整段动画相机保持**上一个视图的朝向**，
直到飞行结束那一帧才被 `controls.update()` 拽正 —— 就是那一下「跳」。

**城市飞行没暴露过这个问题**：它刻意保留方位角，首尾朝向几乎相同，拽不拽正看不出来。
地图 → 文创坊 首尾朝向差得远（`phi` 0.776 → 1.100 且相机横向搬了 1.46），所以原形毕露。

### 证据链（可复算）

1. **录屏逐帧**（`tools/analyze-frames.py --mp4 <录屏>`）：
   全片只有一处孤立单帧尖峰 —— `f0063  diff=8.64  前一帧=0.05 后一帧=0.02`。
   判据是「前后两帧都近乎静止、只有它自己很大」，而不是单纯最大差值
   （f0129-f0134 差值 3.5~4.9 但邻帧同样大 ⇒ 正常动画，正确放行）。
2. **探针逐帧**（`tools/probe-switch2.mjs 2560 1440`）：
   跳变帧 `camera.position / controls.target / fov / aspect` **全都没变**，
   灯笼投影中点却单帧跳 **581.79px**，间距同时缩 17.45px（离轴透视畸变消失）。
3. **地标追踪**（`tools/track-landmark.py`）—— 最直观：
   ```
   改前: t=1163 灯笼(514.0, 93.6) 位移 0.00px 速率 0.0000  ← 完全静止
         t=1173 灯笼(518.4,387.8) 位移 294.18px 速率 29.42  ← 单帧跌 44% 屏高
         t=1181 灯笼(518.3,387.8) 位移 0.08px 速率 0.0101   ← 又完全静止

   ```
   294px / 672 高 = **44% 屏高**；用户录屏 607px / 1345 = **45%** —— 同法同量，吻合。
4. **A/B 单行对照**：只把新增的 `camera.lookAt(controls.target);` 注释掉，其余一字不动，
   用 `tools/probe-frames.mjs`（CDP screencast 真实合成帧）各录一遍，
   结果见上表 —— 跳变只在停掉那行时出现。

### 修法

`tick()` 飞行分支里，lerp 完 position/target 之后补一句：

```js
camera.lookAt(controls.target);
```

放在 lerp **之后**：终点那一帧朝向就等于 `controls.update()` 会算出的结果，
所以随后恢复 controls 也不会再动一下。城市飞行自动同享（首尾朝向本来就几乎相同，无副作用）。

### 顺带全项目排查：这个坑只有这一处，且项目里早有正解参照

「补间期间没人管朝向」是通用模式，所以顺手查了另外两个场景会不会同样中招。
手法（排除 `vendor/` 与 `node_modules/`）：

```bash
grep -rn "lerpVectors\|slerp\|camera\.lookAt\|flyTo\|tweenCamera\|animateCamera" \
  --include=*.js --include=*.html --include=*.ts --include=*.tsx . \
  | grep -v "/node_modules/" | grep -v "/vendor/" | grep -v "\.workbuddy"
grep -rn "TWEEN\|gsap\|@tweenjs\|animejs" ...   # 有没有补间库
grep -rn "camera\.position\.\(set\|copy\|add\|sub\|lerp\)" ...   # 别的补间手法
```

**结论：干净。**

- 全项目**没有任何补间库**（无 TWEEN / GSAP / animejs）。
- 除 `场景选择页面/index.html` 的 `flyState` 之外，所有相机位置改动都是**瞬时** `set` / `copy`
  （葛镜桥 `viewer.js` 的视角预设、文创 `meshUtils.ts` 的摆位、`model-inspect.html` 等），
  不存在「渐变过程中朝向没人管」。
- 苏州双桥是 Unity WebGL，相机在 Unity 内部，不属这个代码面。

**⚠️ 但发现一个很有价值的参照：`贵州葛镜桥/js/drone.js` 早就正确处理了同一个坑。**
它进漫游时也 `controls.enabled = false`（第 127 行），但**自己接管了朝向**：

- 第 122–125 行：从当前 `camera.quaternion` 反解 yaw/pitch 作为起点（YXZ）
- 第 157–159 行：`update(dt)` 里每帧 `camera.quaternion.setFromEuler(this._euler)`
- 第 139–143 行退出时，注释写得很明确：
  > `// 轨道控制器需要一个 target：取当前视线前方一点，保证退出瞬间画面不跳变`
  > `this.camera.getWorldDirection(_fwd);`
  > `this.controls.target.copy(this.camera.position).addScaledVector(_fwd, 0.3);`

即：**禁用 controls 时必须自己喂朝向；交还给 controls 前必须把 target 挪到当前视线上。**
两条原则本项目已有先例 —— 所以场景选择页飞行分支漏掉 `lookAt` 属于**遗漏，不是设计**。
以后新写任何"禁用 controls 的相机动画"，直接照 `drone.js` 这两条办。

## 22:0x —— 进场动画 v2：开门与推进**同时**、到门面即跳、门后做出空间

v1 是「门开完→停顿→穿进房内跳转」，用户反馈三点：
① 门后是实心墙皮，看不出有空间；② 开门和镜头推拉要**同时**；③ **到门那里就跳**，不用穿进去。
v2 全部解决，e2e 仍 48/48。

### ① 空间感：屋身从「一整块实心 box」拆成「门楣+左右墩+暗色内腔」

原来 `wall = box(bodyW, bodyH, bodyD, M.wall)` 是实心 —— 门一开露的是米色墙皮。
拆法（**外观零变化**，同材质、互补尺寸）：
- 门洞：x ∈ [±0.047]、y ∈ [0.027, 0.106]（洞下沿用 bodyY、上沿用门板顶）
- 左右墩 `box(0.0705, 0.079, bodyD)`、门楣 `box(0.235, 0.039, bodyD)`
- **背封板**：补上原实心 box 背面被拆掉的那一块（`box(0.094, 0.079, 0.006)` @ z=-bodyD/2+0.003，
  M.wall）—— ⚠️ 不补会从房子背后看穿堂。
- 门洞常量提级为 `DOOR_HW/DOOR_TOP/DOOR_Y/DOOR_HH`，门循环的 `HINGE_X` 改用它（铰链=门洞外缘，同一事实来源）。

门后**暗色内腔**（`darkIn` 0x1d140d，五面板围出进深 ≈0.068）：
后壁(z=0.020) + 左右壁(x=±0.044，离墩内侧面 0.003 防 z-fight) + 顶(y=0.103) + 地板(y=0.029)
+ 一盏腔内暖灯（小球 emissive 0xff9c3f@0.6，**挂左后角偏离中轴** ——
相机穿门末帧正对门心，灯在中轴会顶成一团正圆橙光像太阳，挪开才是「店内角落一盏灯」）。

⚠️ 内腔不穿模自查：相机穿门时刻 z=0.090，那时 y≈0.083 < 门洞上沿 0.106 ✓；
侧窗(x=±0.079)、立柱(±0.1105)都在墩块区域，门洞区域没它们 ✓。

### ② 同时性：开门与抵近飞行并行（删掉串行的 hold）

- `flyToShop` 触发时**立即** `startDoorAnim()`（开门 0→620ms），同时 `flyTo(...)`（抵近 0→900ms）。
  门在镜头眼前越开越大，抵近站稳时门正好全开。
- fly 的 `then` 接 `startDoorPush`（push 0→1200ms）。
- ⚠️ **open 段只转门，不动 target** —— target 由并行的 flyState 管着，两边同时改会打架。
- 删掉了 v1 的 hold（110ms 停顿）和「open 段下移视线」——视线瞄准门心的活交给 push 段。

### ③ 到门即跳：按「相机与门面距离」双阈值提前压暗/跳转

push 的 p1 仍设在门内一点（z=0.06，保证路径真的穿过门面），但 veil/跳转不再等走完：

## 22:4x —— 进场动画 v3：视角压低平视大门、消灭推进前的"停顿"、到门口就切

用户对着分镜第 5 格反馈三点：① 分镜到这（门全开正对门）就可以切了；② 视角要比分镜相机
**往下、平视大门**一些；③ 门开了以后镜头向前推**停顿了一会儿** —— 不要停顿直接推。

### 停顿的两个来源（都修了）

1. **静止空档**：v2 openDur=620 < flyDur=900/1200 → 门开完到抵近站稳之间有 280~580ms
   相机完全静止。v3 `startDoorAnim(flyDur - 20)` —— 开门与飞行**同时开始同时结束**。
2. **缓动起步**：push 用 easeInOutCubic，前段几乎不动。v3 改 **easeOutCubic**（起步即最快），
   pushDur 1200 → 700。

### 视角压低

进店飞行焦点从 `shopFocus()`（y=0.135）换成**门心** `(SHOP.x, 0.0665, SHOP.z)`，
phi 从 SHOP.phi=1.10（俯角 ≈27°）换成 **1.45（俯角 ≈7°）** —— 相机终点 y≈0.151，
正对大门平视。⚠️ SHOP.phi 本身没动（那是切场观看语义 + 匾额遮挡约束）；phi 1.45 只在
flyTo 里直传（flyTo 对显式传的 phi 不做 0.60~0.96 钳制）。

### 到门口就切

veilZ 从 faceZ+0.13 提到 **faceZ+0.30**：easeOut 路径解出来 veil ≈ push 后 200ms、
跳转 ≈1.36s（v2 是 1.86s）。分镜第 5 格（门全开贴门）→ 第 6 格（1122ms 压暗）就换景。

### 连带改动

- **e2e 两条旧断言对齐 v3**：`推近后店身落在画面正中`/`飞行焦点=店身中段 y=0.135`
  是 v2 语义，v3 焦点变了必红。改成 `shopOffset(0.0665)` 验「门心落画面正中」+
  `target.y≈0.0665`。为此给 `shopOffset` 加了可选 y 参数（不带参仍是店身中段，别的调用点不破）。
- 门角度断言实测 ±96.9°（420ms @ openDur 880，easeOut 下 0.857×112°，吻合）。
- probe-door.mjs MS 1750→1450（跳转 ≈1.36s）；contact-sheet.py KEYS 改 v3 时序。
- **e2e 48/48 全过**（EXIT=0，门心 dy=-0.00 正中）。
